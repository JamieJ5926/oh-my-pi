# Handoff: Universal execution-backend bridge

## Why this exists
Jamie asked whether the execution-backend bridge is jcode-specific or already a universal harness bridge, since pi and jcode both run through it. The investigation answered that. Follow-on work (third harness adapters, optional schema cleanup, patch capture) goes to a fresh session.

## Current state
- The runtime seam is backend-neutral and proven twice. The coordinator and executor never branch on pi or jcode in control flow.
- A new backend is a new `packages/coding-agent/src/bridge/backends/<name>/{backend,protocol,runtime,index}.ts` module plus small union edits. Edit points are `config/settings-schema.ts` (RoleExecutionBackend union, per-backend profile keys), `task/executor.ts` (ExecutorOptions union), `task/index.ts` (#spawnBackendFields, plus an ensure-factory helper only if the harness needs host tools or pooling), `bridge/index.ts` re-export.
- Irreducibly per harness, no abstraction removes it. Wire protocol, process spawn and readiness detection, event extraction, model attribution, transport recovery, host-tool callbacks.
- The runtime coordinator provides admission, bounded event buffering, UTF-8 truncation, cancellation, telemetry. It provides no retries, no transport recovery, no HUD feed. HUD progress is generic and populated from executor progress, not bridge fields.
- Registry asymmetry. Pi uses a fallback registry, jcode requires a caller-scoped registry from #ensureJcodeFactory. A third backend must pick a regime.
- Two contract generations, split live/dead by current evidence. `bridge/core/` address, directory, and envelope types are LIVE infrastructure. `AgentRegistry` (`registry/agent-registry.ts`) runs on `FileSessionDirectory`, `main.ts` and `session/agent-session.ts` import core address/envelope types, `task/persisted-revive.ts` uses them for revival. The likely-dead part is `bridge/core/backend.ts`: its adapter contracts (`CoreExecutionBackend` with start({address, revival}), `CoreExecutionSession` with send(MessageEnvelope), `BridgeCoreContext`) show no implementer and no consumer in any repo grep, and `package.json` exports no bridge subpath that could expose them externally. Treat deletion as a hypothesis, not settled fact. Two incompatible generic APIs sit in one tree. The runtime contract is the one both backends implement.
- Git state. `packages/coding-agent/src/bridge/` is untracked. Upstream main at 9690622 (2026-08-30) and tag v18.0.8 contain none of the bridge, no `execution_backend`, no `jcode_provider`. Local HEAD is v18.0.8 plus 6 local commits (18f749b roleProfiles, loop guards, self-update disable, batch features).
- Patch advisory. Do not blanket-diff `v18.0.8..HEAD`. Build the patch from the bridge tree plus only the roleProfiles/execution_backend/jcode_provider hunks in tracked files, then verify apply and build on a clean v18.0.8 worktree.
- JCode HUD POC. The jcode-side OMP Agents table reads OMP session JSONL from the jcode window. sessionFile flows through bridge metadata. No JSONL parser exists in harness-side OMP code.

## Decisions kept
- Investigation ran under the Pstack Investigation playbook. Three explorers (core/runtime, backends, harness wiring) plus one synthesizer. Findings at `local://bridge-findings.md`, full explanation at `agent://BridgeExplainer`.
- Verdict, corrected. The runtime contract (`bridge/runtime/contracts.ts`) is a proven candidate seam, exercised by two backends, not yet the one canonical contract. The tree still carries a second generic API (`core/backend.ts`) that all current evidence marks unimplemented dead code. Do not build a second abstraction. First design step before any third harness: audit `core/backend.ts` and its re-exports, remove if unreferenced, decide whether the remaining live core directory layer (address/directory/envelope) renames to something like `session-directory` so nobody confuses it with the execution layer, then `runtime/contracts.ts` stands as the single execution adapter contract. The scoped removal MUST be followed by a package-wide typecheck and the bridge and registry test suites before it counts as settled. No Pi or JCode migration is needed for that step. Both live entirely on the runtime contract and never implement core's.
